## 2. Decisions

### D1. Rust platform (OP-03, ADR candidate 1)

STATED (OP-03, DEMO): stable Rust, axum, tokio, sqlx with SQLite, `regex` with `fancy-regex` as fallback, one container. This ADR confirms them and adds the details below (DERIVED).

| Area | Decision |
|---|---|
| Toolchain | Stable Rust, version pinned in `rust-toolchain.toml`, `Cargo.lock` committed, `edition = 2021` or later. |
| Web | axum on tokio. One `Router` per capability module, merged in the platform module. |
| Data | sqlx (SQLite) with bound parameters only. No `format!` into SQL. No migrations and no schema creation (D2). |
| Regex | `regex` crate first. Username pattern (D5) is expressed as `^[a-z0-9_]{1,30}\n?\z` on the lower-cased input, which needs no lookaround. `fancy-regex` is allowed only for a pattern proven to need lookbehind (mention and hashtag patterns, story 3). Each use is recorded as a ReDoS note: the current patterns are bounded (`{1,30}`, `{1,100}`). |
| Crypto | RustCrypto `pbkdf2`, `hmac`, `sha2`, with `subtle` for constant-time compare, and `rand` (OS rng) for salts. No hand-written crypto. |
| Deployment | A single container with one binary. Same env vars and defaults as `minidon/config.py` (`MINIDON_DATABASE_URL`, `MINIDON_DOMAIN`), same dev address `127.0.0.1:8000` (principles 10). |
| Lints and CI | `cargo clippy -D warnings`, `clippy::unwrap_used` and `expect_used` denied outside tests, `cargo deny` (licences, sources limited to crates.io, no git or path deps outside the repo) and `cargo audit`. `unsafe` is forbidden (`#![forbid(unsafe_code)]`) unless a human-reviewed ADR allows it. |
| Panics | A catch-panic layer maps any panic to the Python 500 response (D3). `panic = "unwind"`. No shared state behind a `Mutex` that a panic could poison. |
| Layout | Modules `accounts`, `following`, `posting`, `timelines`, `notifications`, `moderation` plus `platform` (wiring, errors, config, data access). Shapes follow the gate decisions CF-003, CF-004, CF-006 (D6). |

Why: DERIVED, the PO's reason is one supported runtime, one binary and lower running cost (OP-01, DEMO). axum, tokio and sqlx are the common, maintained stack. Alternatives considered: actix-web (no advantage for this task), rusqlite (synchronous, would need `spawn_blocking`), diesel (migration tooling invites schema changes, which D2 forbids).

### D2. Stored formats and schema (OP-05, ADR candidate 2)

STATED (OP-05, DEMO): Rust reads and writes the existing formats exactly. Rust does not create or migrate the schema. It uses the schema the Python app already makes. The rest is DERIVED.

- Schema is owned by the Python app. The Rust binary opens the database and fails at startup with a clear message if the tables are missing. It never runs DDL. The compatibility tests and the harness create databases through the Python app.
- Enum columns hold the upper-case member names (`'ADMIN'`, `'PRIVATE'`). The API shows the lower-case value. The Rust enums have explicit mapping both ways.
- Datetimes are naive UTC text `YYYY-MM-DD HH:MM:SS.ffffff` in storage and naive ISO with `T` on the wire. The Rust code never stores a zone or a different precision.
- Password hash is the string `<salt hex>$<digest hex>`, lower-case hex, 16-byte salt, PBKDF2-HMAC-SHA256, 100,000 iterations, password as raw UTF-8 with no normalisation and no trimming (GRD-004).
- Access tokens are stored in clear text as the primary key, as today.
- Column lengths are not enforced by SQLite and Rust must not enforce them either (a 31-character stored username must be accepted, D5).
- Both directions are tested: a Python-created database used by Rust, and a Rust-written database used by Python.
- Each new column, cache file or log added by Rust is forbidden in this run. This keeps the GAP-005 waiver valid ("no new data stored").
- The database file mode follows the process umask, as for Python. Not stricter and not looser (S-10).

### D3. HTTP contract (OP-06, ADR candidate 3)

STATED (OP-06, DEMO): contract is the error body shapes, the date format and the 404 and 405 bodies. The auto-generated documentation routes (`/docs`, `/redoc`, `/openapi.json`) are not contract and are not ported. The rest is DERIVED.

- Domain errors: status 400, 401, 403, 404, 409, 422 or 429 with body `{"error": msg}`.
- Framework validation: status 422 with body `{"detail": [...]}`. The two 422 shapes are two contracts. The `detail` entries must match Python's field by field only for the cases the parity suite exercises. Where the exact FastAPI `detail` array cannot be reproduced, that is raised as a DEVIATION for the human before build, not hidden.
- 404 and 405 bodies are `{"detail": "Not Found"}` and `{"detail": "Method Not Allowed"}`.
- Datetimes on the wire are naive ISO with `T`. Null fields are present as `null`, as today.
- Trailing-slash behaviour copies Python (checked by the harness).
- 500 responses. PROPOSED (needs human decision, S-03): Rust returns Python's body `500 text/plain "Internal Server Error"` for panics and unexpected errors, with no internal detail, no SQL and no token or password values.
- Python's 500 paths from lone surrogate passwords and out-of-range 64-bit ids. PROPOSED, needs human decision (S-03): accept a deliberate deviation. Rust returns 422 (or 404 for ids) where Python returns 500. Reason: copying the 500 would also copy the username-existence oracle on sign-in, and `serde_json` rejects lone surrogates at parse time. The deviation is recorded here, the harness whitelists exactly these inputs, and the security reviewer confirms or reverses it. If reversed, a custom pre-parse step must reproduce the 500.
- Request body size. PROPOSED, needs human decision (S-02): the axum default (about 2 MB) would turn a 3 MB registration from 201 into 413. Decision proposed: set the body limit explicitly (`DefaultBodyLimit`) to a value at or above what Python accepts in the suite, and record "no size limit" as a carried-forward weakness with a follow-up. Raising the cap to unbounded is not proposed.
- Unparseable `Authorization` header (non-ASCII, tabs, extra spaces, U+001C to U+001F around the token) gives anonymous access or 401, never 400 or 500. Prefix `Bearer` is case-insensitive and the token is trimmed with Python's whitespace set (`deps.py:20-22`).
- Auth state is read from the database on every request. No cache of accounts, roles, suspension or tokens, and no stateless tokens (S-05, OQ-015).

### D4. Parity harness (OP-07, ADR candidate 4)

STATED (OP-07, DEMO): same requests against Python and Rust, ids and timestamps normalised, a fixed clock, non-ASCII cases, read-only on the Python repository. The details are DERIVED.

- One black-box HTTP suite, run unchanged against both builds (principles 5). A rule counts only if its test first passes against Python `e1fbd3a`.
- Python is started from a copy of the reference (or from a working directory outside the repo) with `MINIDON_DATABASE_URL` always set, `PYTHONDONTWRITEBYTECODE=1`, and dependencies from `uv sync --frozen` (S-04, S-09). The resolved versions are written into the parity report.
- The MET-005 proof is extended with `git status --ignored` on the Python repo, or a file-tree checksum before and after. Ignored files (`minidon.db`, `__pycache__`) would otherwise hide a write that breaks I-29.
- Time is an input (principles 9). Python is run with a controllable clock. DEMO ASSUMPTION about mechanism: a small test-only wrapper in the harness copy patches `utcnow` and does not change the reference repo. Rust takes a clock from the platform module that the harness can set. The clock is not exposed through any production endpoint.
- Normalisation: ids and timestamps replaced by stable placeholders. Nothing else is normalised. Header differences are listed explicitly.
- Required input classes: non-ASCII usernames, passwords and text, multi-byte length cases, the trailing-newline username, `%` and quote characters, case-folding cases (KELVIN SIGN).
- Test data: synthetic dataset built through the Python API (OP-09). Sanitised means any copy of real data has every `access_tokens` row deleted or expired, emails replaced, and hashes kept only for synthetic accounts with known passwords (S-04).
- Differential run: the same request sequence on two copies of one database, compared after normalisation.

### D5. Accounts parity points that platform choices must support

STATED (human-decisions section 5): copy the trailing-newline behaviour. DERIVED for the Rust form.

- Lower-case the username first (full Unicode `to_lowercase`), then match `^[a-z0-9_]{1,30}\n?\z`. No `strip()` on the username. Email is trimmed as in Python.
- `alice` and `alice\n` are two accounts (201 each). `alice\n\n` and `\n` give 422. `ALICE\n` after `alice\n` gives 409. A 31-character stored name is accepted.
- The Rust code carries a comment at the pattern: "Deliberate parity copy of Python `$`-before-final-newline (human-decisions section 5). Follow-up: reject in both builds after cutover."
- Weak password policy (minimum 8) and PBKDF2 at 100,000 iterations are copied. No rehash on login and no new hash format in this run, because a rehash would lock the account out on Python while both builds share data (S-06, GRD-004).

### D6. Cross-capability shapes already decided

STATED (gate record CF-003, CF-004, CF-006): `get_by_username` is a stable identity API owned by Accounts. The social queries module is a plain module owned by Following. Moderation calls Posting's soft delete directly, with the boost cascade. DERIVED Rust form: `accounts::identity` is a public module with `get_by_username` and `get_by_id`. Later stories call it as a function and never read the accounts table directly. The dead `minidon/lists/` code is not ported (CF-002).

### D7. Build order and the Following/Notifications seam (OP-04)

STATED (OP-04, DEMO): Following first with a stub notifier that records the event and does nothing. Notifications second, swapping in the real notifier. DERIVED Rust form: a `Notifier` trait in the platform module with a no-op implementation in story 2 and the real one in the Notifications story. The trait is the only seam. Order: Accounts, Following, Posting, Timelines, Notifications, Moderation, which matches the estimate basis.

## Threat model delta

STRIDE-lite, I-10, story 1 Accounts.

Change surface (DERIVED): five Accounts endpoints (register, sign-in, `me`, profile lookup, profile update), the shared auth extractor, and the password and token stores. No new endpoint, no new data. The rewrite changes where the code runs, not what it exposes. The two risks are accidental change of security behaviour and known weaknesses being forgotten. Rows 1 to 9 come from `research/security.md` and are re-checked here. Rows 10 to 14 are new from the security lane review (S-01 to S-05, S-07).

### Weaknesses carried forward on purpose, with follow-ups

Follow-up numbers are labels for this ADR. Real tickets are raised by the human.

- STATED sources: F-A (trailing-newline username, human-decisions 5), F-B (first admin, OQ-001), minimum password 8 raised to 12 (OQ-002), F-F (hash upgrade, OQ-003), audit trail for staff deletes (OQ-009).
- DERIVED additions from the security lane: F-C no sign-in throttling and enumeration (409 messages, timing, suspended-403), F-D no body size limit and the Python 500 paths, F-E clear-text tokens at rest (no gate follow-up names this), F-G no sign-out or revocation endpoint, F-H no audit trail for suspend and role changes, F-I delete existence oracle and the two-step admin suspension.
- Constraint on F-F: the stored hash has no iteration marker and Python hard-codes 100,000, so a rehash in one build locks the account out of the other. The follow-up must change both builds together or wait until cutover.
- GAP-005 "revisit at cutover" should be an item on the cutover ticket.

## 4. Consequences

- Positive: one stack, one deployable, parity proven at the HTTP boundary, security behaviour kept as it is and visible.
- Negative: weaknesses are shipped knowingly (the list above). The Rust build cannot create its own schema, so it needs a Python-created database to run. Deviations (D3 lone surrogate, out-of-range ids) are the only intentional behaviour differences proposed.
- Reversible: crate choices can change by a later ADR. The stored formats cannot change without a migration, which is out of scope.

## 5. Decisions that need a human before build

All are DERIVED proposals. None is made by design-agent (I-23).

Decided on 2026-11-13. Decision owner: kurtis. DEMO ASSUMPTION: the user asked Claude to draft reasonable answers for the demo, so these are plausible guesses written in the user's name. In a real team the Tech Lead and a security reviewer would decide.

1. Lone-surrogate password and out-of-range id (S-03). DECIDED: accept the 4xx deviation. Python returns a 500 here, which is a crash and not designed behaviour. Rust returns a 4xx, and the deviation is listed in the parity test as a known difference.
2. Request body limit (S-02). DECIDED: set a 1 MiB limit. Rust returns 413 above it, where Python accepts the request. This is a recorded deviation.
3. FastAPI `detail` arrays for 422 (D3). DECIDED: accept the stated limit. Rust matches the status code and the top-level error shape. It does not copy the exact text of each validation message, because no known client depends on it.
4. Security reviewer sign-off (S-01). DECIDED: kurtis confirms the carried-forward list as the DEMO security reviewer, including the look-alike username. Fixing it is a follow-up after cutover.
5. Crate list in D1 and `cargo deny` policy (S-09). DECIDED: approve the crate list as written. `cargo deny` blocks known advisories and unknown registries, and allows only MIT, Apache-2.0 and BSD licences.

Added on 2026-11-13 after plan review 001 (`reviews/plan-review-001.md`). Same DEMO ASSUMPTION: drafted by Claude in the user's name.

6. Lone-surrogate input beyond password and id (plan review M-03). DECIDED: error body shapes are contract (OP-06), so they are not traded away.
   - A username with a lone surrogate must return Python's 422 with an `{"error": ...}` body. Rust adds a pre-parse step for this case, and does not let the generic `{"detail": ...}` body through.
   - An email, display name or bio with a lone surrogate that passes validation is a Python 500 (SQLite cannot encode it). Rust returns a 4xx, as in decision 1. This is a recorded deviation.
   - A sign-in with a lone-surrogate password for an unknown user returns 401, as Python does, because Python never reaches the hash.
   - The plan must list every input class and field with its Python and Rust outcome. The harness whitelists only the deviations named here.
7. Extra crates (plan review M-06). DECIDED: approve serde, serde_json and tower-http as runtime crates, base64 and hex for the token and hash encodings, and the `time` crate for dates (not chrono). reqwest and tempfile are dev-only, for the harness and tests. The plan must list each crate with version, licence and reason. The licence policy in decision 5 still applies, and `cargo deny` must pass before wave 0 merges.

Consequence: the deviations in decisions 1, 2 and 6 must appear in the test plan as known differences from Python. Parity is otherwise unchanged.
